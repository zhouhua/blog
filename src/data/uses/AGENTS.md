# 在用

`/uses` 记的是喜欢的、还在用的东西。技术栈只是可能出现的一种内容，不是页面本身，也不是默认分类。

添加、修改、移动条目时先读这份说明，再改同目录的 `index.ts`。页面按 `USES_GROUPS` 渲染，不要到 `src/pages/uses.astro` 里硬编码分类。介绍文章、卡片 logo 和头图见 `.cursor/skills/add-uses-content/SKILL.md`。

## 添加时怎么做

1. 先读当前的 `USES_GROUPS`。没有分组时，数组是空的。
2. 只加用户这次明确说的东西。不要根据仓库依赖、常识或「应该也喜欢」补条目。
3. 同一次提到的几条一起归类，避免拆成意思重复的组。
4. 对每一条，先定父分类，再定它放在父分类的 `items` 里，还是某个子分类里：
   - 任何分组或子分类里已有同名条目：改那一条，不要再插一条。
   - 某个已有分组的 `title` 不用改写也装得下：用这个分组。否则新建分组，放在数组末尾。新组必须带上这一条，不要建空组。
   - 分组确定后，按下面的「子分类」决定落点。装进已有子分类时，追加到该子分类的 `items` 末尾。没有子分类、也不该新建时，追加到父分类的 `items` 末尾。

## 沿用已有分类

沿用，当这条和该组已有条目是同一种东西，放进去之后原来的 `title` 仍然成立。

如果差一点点，优先判断 `title` 还能不能准确概括，而不是新开一组。改完标题之后什么都能往里放，就不要改，改为新开一组。

不要因为两条都是「软件」或都是「喜欢的」就放进同一组。子分类也按同一标准：已有子分类装得下，就放进去，不要再开一个近义子分类。

## 新建分类

新建，当现有分组都装不下，除非把边界放宽到失去意思。

新组的名字用种类，不用这一条的品牌。这个名字以后还装得下同类的第二条。只为眼前这一条造一个无法再装别的东西的名字时，把名字提高一层，但不要提高到「其他」「杂项」「未分类」。这些名字不要用。

技术栈、库、Skill、工具都不是预留组。用户添加的内容确实属于某一类时，那一类才出现。

## 子分类

大多数分组不要 `subgroups`，条目直接放在 `items` 里。

一个分组里的条目能按种类分开，而且分开后更好读时，才用子分类。用户说明这一类会持续收集很多（例如 skills）时，一旦能看出种类就建子分类，不必等列表变长。

子分类可以暂时只有一条，只要这个名字以后还装得下同类的下一条。看不出种类、又不值得单开的，留在父分类的 `items`。一条只出现在一个地方。

子分类不再往下分。不要用「其他」「杂项」「未分类」当子分类名。不要为了对称，给没有这种需要的分组加子分类。

## 字段

分组：

- `id`：英文短横线，创建后不要改，除非用户要求。不要用第一条的名字当 `id`。页面上所有分组和子分类的 `id` 都不能重复。
- `title`：短中文，通常 2 到 6 个字。大分类不要写 `description`。
- `items`：直接属于这一组、还没进子分类的条目。
- `subgroups`：可选。没有子分类就省略。
- 组的顺序、组内条目的顺序都保持追加顺序，不要重排。

子分类：

- `id`：`{父分类 id}-{种类}`，例如父分类是 `skills`，写作类是 `skills-writing`。
- `title`：短中文。用种类，不用某一条的名字。
- `description`：标题已经说清楚就可以省略。
- `items`：这一类的条目。不要建空的子分类。

条目：

- `name`：用用户的叫法。
- `note`：必填。一两句，先说它是什么，再说具体做什么。用户说过理由就用用户的话；没说就按它实际是什么写。不要写成「因为很好用」。
- `href`：用户给了链接就用。没给时，只有官方地址明确才补；不确定就省略。
- `logo`：可选。有明确的官方 logo，或用户给了参考图，就按那个做。找不到时，用它所在处的图标加上名称，例如 GitHub 图标加名称。自带底色的彩色图不要在深色模式反色，只有深色单色标才设 `invert: true`。只有像素图才设 `pixelated: true`。

## 不要做

- 不要预先填分类、子分类或示例条目。
- 不要在同一次修改里新建组，又把没被要求整理的旧组拆开或合并。
- 不要给子分类再加子分类。
- 不要改导航文案、页面标题或地址，除非用户在说名字。
